## PLL のロックを、その PLL が作るクロックで同期している

**状態**: 構造として指摘できる。ただし**実害があるかは未確認**。直していない。

フレームワークがコアを「準備完了」と判断する材料は、これだけ。

```systemverilog
// core_top.sv:279-280
wire status_boot_done  = pll_core_locked_s;
wire status_setup_done = pll_core_locked_s;
```

`pll_core_locked_s` は PLL のロック信号を 3 段のフリップフロップに通したもので、
そのクロックが `clk_ram`。

```systemverilog
// core_top.sv:510
synch_3 s01 (pll_core_locked, pll_core_locked_s, clk_ram);
```

そして `clk_ram` は、**その PLL の出力 0**（67.108860 MHz）。

```systemverilog
// core_top.sv:561-571
mf_pllbase mp1 (
  .refclk   ( clk_74a         ),
  .rst      ( 0               ),   // ← リセットは常時不活性
  .outclk_0 ( clk_ram         ),   // ← 上の同期回路のクロック
  .locked   ( pll_core_locked )
);
```

**観測したい信号が真でないと、観測するためのクロックが動かない。** PLL がロック
しなければ `clk_ram` は止まったまま、同期回路は一度もクロックされず、準備完了は
永久に立たない。`rst` が 0 固定なので PLL がやり直すこともない。**一度悪い立ち
上がりをすると、FPGA を再構成するまで抜けられない一方通行。**

### なぜ直していないか

- **一度も再現していない。** 手元の Pocket では毎回起動する。
- この配線は**上流（budude2/openfpga-GBC）から変えていない**。APF のテンプレート
  がこの形をしている。上流で問題になっていない以上、これ単独が原因とは言えない。
- 直すとしたら `clk_74a`（PLL に依存しない外部クロック）で同期する形になるが、
  **こちらで再現しない以上、直ったかどうかを確認する手段がない。** 報告者が
  「直った」と言っても、間欠故障なのでたまたま出なかっただけかもしれない。

### 上流から変えたところ（関連しうる）

PLL の出力周波数。brickboy のラスタ（896×627 @ 33.554432 MHz）を出すため、映像
クロックを **5 倍**にしている。

| 出力 | 上流 | 現在 | 用途 |
|---|---|---|---|
| 0 | 67.108860 MHz | 同じ | `clk_ram` |
| 1 | 33.554430 MHz | 同じ | `clk_sys` |
| 2 | **6.710885 MHz** | **33.554430 MHz** | `clk_vid` |
| 3 | **6.710885 MHz** (90°) | **33.554430 MHz** (90°) | `clk_vid_90` |

位相シフトは 37253 ps → 7451 ps。どちらも周期の 1/4（90°）で、周波数変更に合わせ
て正しく再計算されている。

### 関連する報告

[Issue #4](https://github.com/kathoc/brickboy-dmg-fpgacore/issues/4)
"Error in framework / Core not ready to run"（willschupp-design、2026-08-18）。

報告者から得られた事実:

- `sleep_supported: false` にしても**直らない**（当初のスリープ復帰仮説は外れ）
- カートリッジでも SD の ROM でも起きる
- スリープ復帰だけでなく**メニューからの起動でも**起きる
- 他のコアでは一度も無い（長年の Pocket ユーザー）
- **別のコアを読んでから戻ると直る**

最後の 1 点は、上の一方通行が予測する挙動と一致する。ただし**一致することと、
それが原因であることは別**。

### 再現できたら、この順で確かめる

1. `pll_core_locked` を `clk_74a` で同期する版（PLL に依存しないクロック）。
   これで消えるなら、ブートストラップが原因。
   注意: `pll_core_locked_s` は SDRAM の `init`（core_top.sv:785）でも使っている
   ので、同期回路を差し替えるのではなく status 用に別途立てること。
2. 1 で消えないなら、`status_boot_done` / `status_setup_done` を PLL から切り離した
   版（`clk_74a` のカウンタ等）。これで起動するなら準備完了の経路の問題、
   起動しないなら構成そのものの問題。

間欠故障なので、「消えた」と言うには**失敗率を先に測る**こと。報告者は当初
「スリープ復帰でほぼ毎回」と書いている。
